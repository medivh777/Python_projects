# pg_plan_monitor

Мониторинг PostgreSQL с хранением истории в **ClickHouse** и веб-интерфейсом:
планы запросов, алерты при смене плана, active session history (ASH),
блокировки, графики statements (как в temboard) и рекомендации по индексам.

## Возможности

| # | Что | Где |
|---|-----|-----|
| 1 | Список запросов: query_id, текст, среднее/макс/суммарное время, вызовы, I/O, число планов | `/queries` |
| 2 | Сравнение планов + **алертинг при смене плана** (индекс → Seq Scan = critical, смена индекса/джойна = warning) | `/alerts`, `/query/<id>` |
| 3 | Мониторинг активных сессий как pg_activity + ASH (семплы в ClickHouse, график средних активных сессий по типам ожиданий) | `/activity` |
| 4 | Детализация запроса: графики, история планов, таблицы и индексы запроса, запросы по тем же таблицам | `/query/<id>` |
| 5 | Графики statements как в temboard: время выполнения, calls, чтение диск/кэш, temp/WAL, CPU/RAM/диск хоста | `/` (дашборд) |
| 6 | Блокировки: кто кого блокирует сейчас + история за неделю (TTL 7 дней) | `/locks` |
| 7 | Рекомендации по индексам: создать (по Seq Scan из планов), удалить неиспользуемый, убрать дубликат | `/recommendations` |

## Архитектура

```
PostgreSQL (наблюдаемый)          ClickHouse                Веб (FastAPI)
┌─────────────────────┐   писать  ┌───────────────┐  читать ┌─────────────┐
│ pg_stat_statements  │──────────▶│ statements_*  │◀────────│ дашборд     │
│ pg_stat_activity    │ коллектор │ ash, locks    │         │ запросы     │
│ pg_locks            │  (python) │ query_plans   │         │ активность  │
│ EXPLAIN (планы)     │           │ plan_alerts   │         │ блокировки  │
│ pg_stat_*_tables    │           │ recommendations│        │ алерты      │
└─────────────────────┘           └───────────────┘         └─────────────┘
```

Ключевой принцип — **не грузить наблюдаемую БД**:

* веб-интерфейс ходит **только в ClickHouse**, PostgreSQL не трогает вовсе;
* коллектор читает только статистические представления (разделяемая память,
  без обращения к данным таблиц);
* `EXPLAIN` (не ANALYZE!) выполняется редко (раз в 5 минут, только топ-50
  запросов), в транзакции с `ROLLBACK` и `statement_timeout = 3s`;
* план сохраняется в ClickHouse только если изменился (по фингерпринту);
* размеры таблиц/индексов снимаются раз в 10 минут;
* ASH-семплы буферизуются и пишутся в ClickHouse пачками.

## Быстрый старт (docker compose)

```bash
cp config.example.yaml config.yaml   # поправьте DSN при необходимости
docker compose up -d --build
# веб: http://localhost:8080
```

В составе — демо-PostgreSQL 16 с уже включённым `pg_stat_statements`.
Для мониторинга своей БД удалите сервис `postgres` из compose и укажите свой
DSN в `config.yaml`.

## Подключение боевой БД

1. В `postgresql.conf`:

   ```
   shared_preload_libraries = 'pg_stat_statements'
   pg_stat_statements.track = all
   compute_query_id = on        # query_id в pg_stat_activity (PG >= 14)
   track_io_timing = on         # время дискового I/O
   ```

   и перезапустите сервер.

2. Выполните `sql/pg_setup.sql` (создаёт роль `pgmon` с правами
   `pg_monitor` + `pg_read_all_data` и расширение `pg_stat_statements`).

3. Пропишите DSN в `config.yaml` и перезапустите коллектор.

Требования: **PostgreSQL 13+** (для планов параметризованных запросов через
`EXPLAIN (GENERIC_PLAN)` — **PostgreSQL 16+**), ClickHouse 23+.

## Запуск без Docker

```bash
pip install -r requirements.txt
cp config.example.yaml config.yaml            # укажите свои PostgreSQL и ClickHouse
python -m pgmon.collector.main                # коллектор
uvicorn pgmon.web.app:app --port 8080         # веб-интерфейс
```

## Как снимаются планы и работает алертинг

1. Раз в `intervals.plans` секунд берётся топ-`plans.top_n` запросов по
   суммарному времени из `pg_stat_statements`.
2. Для каждого выполняется `EXPLAIN (FORMAT JSON)` в его БД; параметризованные
   запросы (`$1`) — через `EXPLAIN (GENERIC_PLAN)` (PG16+).
3. Из плана строится **фингерпринт** — хеш структурного скелета (типы узлов,
   таблицы, индексы, типы соединений) без стоимостей: колебания cost не создают
   ложных «новых планов».
4. При изменении фингерпринта план сохраняется и создаются алерты:

   | Изменение | Уровень |
   |---|---|
   | Индексный доступ → Seq Scan | **critical** |
   | Смена индекса на таблице | warning |
   | Смена метода соединения (Nested Loop / Hash / Merge) | warning |
   | Рост стоимости ≥ 5× (настраивается) | warning |
   | Seq Scan → индекс (улучшение), прочее | info |

Алерты видны на `/alerts`, в бейдже навигации и в карточке запроса.

## Рекомендации по индексам

* **Создать** — в свежих планах есть Seq Scan c фильтром по большой
  (>10 МБ) таблице, и ни один существующий индекс не покрывает колонки
  фильтра. Генерируется готовый `CREATE INDEX CONCURRENTLY ...`.
* **Удалить** — `idx_scan` индекса не вырос за весь период наблюдения,
  индекс не уникальный и не первичный ключ.
* **Дубликат** — колонки индекса являются префиксом другого индекса той же
  таблицы.

DDL из рекомендаций применяйте осознанно и сначала на тестовом стенде.

## Схема данных в ClickHouse (база `pgmon`)

| Таблица | Что хранит | TTL |
|---|---|---|
| `statements_metrics` | дельты pg_stat_statements по интервалам | 90 дн |
| `queries` | тексты запросов по queryid | — |
| `query_plans` | планы (JSON + метаданные), только при изменении | 90 дн |
| `plan_alerts` | алерты о смене плана | 90 дн |
| `ash` | семплы активных сессий (раз в 2 с) | 14 дн |
| `locks` | пары «кто кого блокирует» | **7 дн** |
| `sysstat` | нагрузка: сессии, транзакции, I/O, CPU/RAM хоста | 90 дн |
| `table_stats`, `index_stats` | снапшоты статистики таблиц/индексов | 90 дн |
| `recommendations` | рекомендации по индексам | — |

Все TTL настраиваются в секции `retention` конфига.
